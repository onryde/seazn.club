## 3. Issues

### Important

**I1 — `scoring-undo-codes.test.ts:14-32`: the shape guard has no case that
defeats it.** Both tests feed a payload that already trips
`scoring.ts:284`'s predicate, and both expect the same constant. Delete the
`if` entirely and throw `UNDO_NOOP` unconditionally: both stay green.
Removing only the `typeof eventId !== "string"` half also stays green, because
`UUID_RE.test(undefined)` stringifies to `"undefined"` and still fails to
match. The mutant is killed only by `device-links.test.ts:208-214`, which
drives a *successful* `core.void` through `scoreEvent` — and that suite is
`describe.skipIf(!HAS_DB)`, so it is skipped by the documented non-DB
invocation (`DATABASE_URL=`) this wave's own gates use. *Fix:* add a third
case with a well-formed UUID and assert `err?.code` is **not** `UNDO_NOOP`
(it will be a `withTenant` failure without a DB, `UNDO_TARGET_MISSING` with
one). That is the positive pair the two negatives are missing.

**I2 — three of the four wire codes are asserted nowhere, and the literals are
re-typed in three modules.** `scoring.ts:294` `UNDO_TARGET_MISSING`, `:300`
`UNDO_ALREADY_VOIDED`, `:307` `UNDO_NOT_UNDOABLE` have no test in this commit;
the file's own comment defers them to "the wave's regression e2e" (plan Task
9), which does not exist yet. Meanwhile the same four strings are hand-typed
again at `transport.ts:179-182` and `refusal-copy.ts:61-64`. An unrecognised
code falls back to renegotiable **by design** (design §4.3), so a single-letter
divergence at any of the three sites silently reinstates the exact wedge this
wave exists to close, with a green suite. *Fix:* export one
`const UNDO_REFUSAL_CODES = [...] as const` that all three sites import, or —
cheaper — a test that imports the terminal set from `transport.ts` and asserts
every code `scoring.ts` throws is a member of it.

**I3 — `rate-limit.test.ts:141-146` is decoration, and its name and comment
both misdescribe it.** Titled "is inert when no counter is configured", it in
fact *configures* a counter that returns `null`. Its comment (`:136-140`)
claims it pins one of the two `count === null` routes told apart by
`cacheEnabled()` — but the config omits `failClosed`, so `rate-limit.ts:60`'s
`failClosed && cacheEnabled()` short-circuits at `failClosed` and
`cacheEnabled()` is never evaluated. It is behaviourally identical to `:64-67`
("fails open by default"). Delete it and no mutant survives that was not
already dead. *Fix:* rename to "a configured counter returning null fails
open", or make it differ by setting `failClosed: true` and varying
`cacheEnabled`.

**I4 — replay hits are now entirely unrate-limited (`scoring.ts:97-103`).**
Taking the three abuse paths in turn: an unauthenticated caller is unchanged
(`requireFixtureActor` at `route.ts:15` still precedes everything); a caller
spamming *random* idempotency keys is unchanged (cache miss → limiter runs);
but a caller replaying a *known* key now has no limit at all. A `dl_` secret is
a shareable URL, so this is reachable by a leaked link. The design's "same cost
class as the limiter's own INCR" is true about cost and conflates cost with
boundedness — the bound is not cheaper, it is gone, and each request is a
billed Upstash GET. Mitigating: the DB query in `requireFixtureActor` was never
behind this limiter anyway, so DB exposure does not change. *Fix:* keep the
ordering and add a generous second bucket on the replay path (e.g.
`rl:scorereplay:<fixtureId>` at 60/s), or peek-then-charge.

**I5 — `PadHostV3Props.auth` is optional (`pad-host.tsx:1518`), which preserves
the exact shape that let this bug ship inert.** Optional prop plus a silent
`?? SESSION_AUTH` default (`use-pad-pipeline.ts:1141`) is why tsc stayed green
for months while every device-link pad polled. `<PadHostV3` has exactly one
production mount (`registry.tsx:289`; the only other hits in `apps/web/src` are
comments in `__tests__/registry.test.tsx`), and `ScorePadProps.auth` is already
**required** (`registry.tsx:205`). *Fix:* drop the `?`. The next drop then
becomes a compile error instead of a silent 15s poll.

**I6 — the new e2e asserts the request and never the answer
(`device-links.spec.ts:133,152-153`).** `route.continue()` discards the
response. If the token door's device-link bypass
(`api/v1/public/fixtures/[id]/realtime-token/route.ts:46`) regresses, the
header is still exactly right, the test is still green, and the pad is back on
the 15s poll — the customer-visible outcome is unpinned. *Fix:* one line —
`const r = await route.fetch(); expect(r.status()).toBe(200);` then
`await route.fulfill({ response: r })`.

### Minor

**M1 — no test-budget raise on a test with two 20s polls under a 60s file
timeout.** `playwright.config.ts:135` sets `timeout: 60_000`; the new test does
seed + generate + mint + `goto` + a 20s visibility poll
(`device-links.spec.ts:139`) + a 20s header poll (`:141-146`). On a slow runner
this blows the budget, and the runner then prints the in-flight poll's own
message — "the pad never asked for a realtime token" — above the timeout line,
i.e. a wall-clock failure reported as a data defect. *Fix:* `test.slow()` or an
explicit `test.setTimeout`, expressed against the poll constants rather than a
flat literal.

**M2 — `rate-limit.test.ts:149-154` claims an `http.ts` mapping it never
exercises.** The title says "so http.ts maps 429"; the body asserts only that
`err.code` is `undefined`. Nothing in `http.ts:239`'s
`err.code ?? statusCode(err.status)` is executed, and `err.status` is not
asserted either. *Fix:* assert `status === 429` as well, and either rename or
import `statusCode` and assert the resulting envelope code.

**M3 — design §4.3 (`2026-09-21-device-link-scoring-gaps-design.md:141`) lists
only three codes** mapping to `kind: "rejected"`; `UNDO_NOT_UNDOABLE` is
absent, although §4.1 (`:116`) adds it as the fourth and flags that it was
found late. An implementer working from §4.3 leaves "undo an undo"
renegotiating and the wedge alive for that case. The plan and the transport
working tree do carry all four, so the live risk is to future readers only.
*Fix:* add the fourth code to §4.3's list.

**M4 — `scoring-replay-is-free.test.ts:51` swallows every error**
(`.catch(() => undefined)`). Acceptable as written — the `seen` assertion still
carries the test — but a 429 from the limiter itself would be invisible. *Fix:*
assert the caught error is not a 429 before asserting `seen`.

### Answered directly

**`__assertUndoTargetForTests` (`scoring.ts:315`) — acceptable here.** It is a
`const` alias, not a re-implementation, so a rename of `assertUndoTarget` moves
it automatically and it cannot drift. There is in-repo precedent in this very
commit (`__setRateLimitCounterForTests`). Two caveats, neither blocking: the
JSDoc's "module-private by intent" is now false of the module's actual export
surface, and the seam invites a future contributor to test the three DB-backed
codes through a mocked `withTenant` — which the test file's own comment
correctly forbids. Worth one `no-restricted-imports` rule if the pattern
spreads; not worth a change now.

- **No external consumer of the old `CONFLICT` code breaks.** `http.ts:82`'s

- **No i18n owed by these two commits.** All four undo messages are
  byte-identical to their pre-commit text; only the machine `code` argument is
  new. Neither commit adds a user-facing string.
- **CI coverage exists.** `device-links.spec.ts` matches `SERIAL_SPECS`

  "server-only"`, so no client bundle carries it.

## 5. Three lenses

**Customer.** One reachable surface: `48671ff94` moves a courtside device-link
pad from the 15s poll to realtime, which is correct and is the change the owner
saw missing on staging. It changes no copy. `22a45fb24` changes nothing a
person sees — the messages are unchanged and the codes have no consumer yet
(gap hunt, bullet 1), so "the scorer now gets a calm 'already undone' instead
of a wedged queue" is not yet a true statement about the product. The one
customer-outcome gap in the diff is **I6**: the e2e proves the pad asks
correctly, never that the door answers.

**Product owner.** Both commits solve their half of the stated problem rather
than a proxy, and both are close to minimal — two prop lines, four third
arguments, one statement reordered. The `counterOverride` seam is a production
edit justified only by testability, but design §4.7 sanctions it explicitly, so
it is not creep. Nothing here is irreversible: no migration, no schema, no data
write, no destructive call. Who is hurt if it ships wrong: **I2** is the one
that costs a match — a typo in any of three hand-typed code lists silently
restores the wedge and a scorer loses rallies; **I4** costs Upstash spend, not
correctness. **M3** is a spec inconsistency that would cost the next
implementer one of the four cases.

**Test design.** The money path is covered directly, not incidentally
(`scoring-replay-is-free.test.ts` drives real `scoreEvent` with a real
differential). No DOM-lying tests. Expected values are mostly hand-typed: the
limiter key at `scoring-replay-is-free.test.ts:47` is a benign one (drift reds
it rather than hiding), the four undo codes are the dangerous kind (**I2**).
The defects are **I1** (a guard with no defeating case), **I3** (a case that
adds nothing and whose name asserts the opposite of what it does), **M2** (a
title claiming coverage the body lacks) and **I6** (the assertion stops one hop
short of the outcome).

## Verdict

**Needs fixes.** The production changes are correct and minimal, but the four
wire codes — the whole contract this wave turns on — rest on hand-typed
literals in three modules with only one of them tested, and the one guard that
is tested cannot be defeated by its own test file.
