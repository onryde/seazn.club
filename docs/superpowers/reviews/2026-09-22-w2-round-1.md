## Findings — three, all found by tests rather than by reading

### F1 (BLOCKING, fixed) — the plan's catch would have shipped inert

The plan and design §6 both said a duplicate arrives as a `23505`. It does
not, and `23505` is not even the common shape: `appendEvent` compares
`expected_seq` against the ledger tip (`append-event.ts:198`) and raises
`SEQ_CONFLICT` **before attempting the insert**. A sequential retry — the
actual scenario this wave exists for — therefore never reaches the unique
index, and a `23505`-only catch would have answered every real retry with a
`409`.

Caught red: `EngineError: expected seq 1 but ledger is at 2`.

Fixed by matching both shapes and gating on the ledger lookup rather than the
error code. Recorded in the plan, in the design doc's new "As built", and as a
durable memory.

### F2 (fixed) — my own test set could not kill a dropped guard

Mutant M7b (remove the `if (replayed)` gate, answer unconditionally) survived
the first four cases. Nothing distinguished "answer from the ledger" from
"swallow any `SEQ_CONFLICT` carrying a key". Closed with a stale-write-with-a-
NEW-key case, which is also a real two-pad scenario; it is the only test that
reds under M7b.

### F3 (fixed) — two branches covering for each other

Mutant M7 (delete the `rateLimit` on the new duplicate branch) survived the
whole suite **including `scoring-replay-is-free.test.ts`**, the file that
exists to pin that limiter. It survived because that file mocks `cacheGet` to
HIT, so every case returns from the CACHE branch and the database branch is
never reached. Closed with a counting test that runs with no cache at all.

**M4 is undead and stays undead.** Every other unique constraint on
`score_events` is guarded ahead of the insert, so no reachable case constructs
one. It stands on the house rule (`slugs.ts:61`, `event-import.ts:84`), not on

**M2 and M3 required a clean database.** The working test DB already holds
cross-fixture duplicate keys and many null keys from the e2e runs, so the
mutated indexes cannot be created there at all — both mutants would have read

**M5's first version was vacuous** and is the sharpest lesson here: the
original rig's later event was `core.finalize`, which adds no score, so
folding the whole ledger produced a byte-identical result and the mutant
survived a 4/4 green suite. Replaced with a `core.void`, which erases the
decision.

## Vacuity checks beyond the mutants

The walkthrough finished in 8.3s — faster than 5 taps × `HOLD_MS` should
allow. Rather than accept the green, M8 was applied (replay carries a
different key) and the walkthrough reds. The death is correct three ways: the
replays genuinely reach the server, the outcome depends on the key surviving
the wire, and the server is not blanket-accepting duplicates.

The API spec carries a permanent internal differential: the "new key, stale
seq" case gets `409` while the "seen key, stale seq" case gets `2xx`, on the
same request shape. So the `2xx` cannot be a server that accepts everything.

The seam was checked before it was tested: the pad really does send a key
(`pipeline.ts:205`, `device-score-pad.tsx:158`, `fixture-console.tsx:465`).
A guarantee whose producer never reaches it is the inert-seam class.

## Migration note

V413 was edited after it had already been applied locally (correct for an
unmerged migration), which left a Flyway checksum mismatch. Repaired with
`flyway repair` — and because repair only rewrites the checksum and does not
re-run the migration, the applied schema was verified directly afterwards:
`indisvalid = t`, unique, on `(fixture_id, idempotency_key)`. That check is not
optional here; this same DB previously held an INVALID index from the
`CONCURRENTLY` attempt documented in V413's header.
