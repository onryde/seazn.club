**Goal:** One arbiter participant per (organizer, meeting) for the life of the game, joins that yield to the check-in line, and every board's presence and camera state read from the server's tables at no vendor cost, for Match Day's board panel to use.

**Architecture:** The join route finds or makes the organizer's participant for a meeting through the ROW (one live arbiter row per organizer per player meeting, kept by a unique partial index; the vendor subject keeps its nonce, because the vendor's answer after a delete is unmeasured), refuses until the side's player has arrived (flag on: a presence row naming the player's participant; flag off: a counted check-in; either way a player participant on file), and refuses `VIDEO_BUSY` while the line's pool is under a 60-call floor. The one predicate for "arrived" (`arbiterSideAdmits`) is shared by the join and the loader, which hands each side a `joinable` mark: the panel joins only a joinable side, so the band poll that already refreshes the page (`startBandPolling`, 20 s while live) is what opens the join the moment the player arrives. The browser keeps each meeting's token in memory once it has connected, closes with the SDK leave only, and runs one join chain per meeting. The loader adds the side's player's presence and browser-reported camera to each side of each board from plan 1's table and the camera-report reader. Match Day's board panel (its own plan) is what joins the cameras.

**Tech Stack:** as plans 1 and 2; React 19 client components under `apps/web/src/components/v2/`, `@cloudflare/realtimekit` 2.0.2 web SDK, the fake SDK in `apps/web/src/components/public-site/match-room/__tests__/_fake-realtimekit.ts`, Playwright.

## Global Constraints

- `ARBITER_JOIN_FLOOR = 60` calls ABOVE THE LINE'S RESERVATIONS: a join takes its token only while the pool (`seat-line.ts linePool(budgetKey)`: the bucket's level minus the admitted stays' stamped reservations, the same arithmetic the gate uses) is at least the floor; below it the route answers 503 `VIDEO_BUSY`. `arbiter.ts` never reads the ledger itself: `linePool` lives in `seat-line.ts` beside `reservedSql`, so the one-reader guard holds: in `apps/web/src/server/external-play/__tests__/seat-line-one-reader.test.ts`, `FRAGMENT_USES.reservedSql` gains `linePool: 1` (a fifth use beside today's `readStanding: 3, lineActive: 1`; `readStanding` keeps its own sum under the lock), the consumer table that pins callers outside the module per file and declaration (`SITES`) gains `{ file: "server/usecases/external-play/arbiter.ts", owner: "joinAsArbiter", fn: "linePool", times: 1, consumer: "the arbiter join's floor" }`, and `SEAT_LINE_API` gains `"linePool"` (the list of seat-line functions whose callers `SITES` pins; without it the new caller is not scanned). With no vendor configured (`currentBudgetKey()` null) there is no bucket and no floor.

With it unset the join refuses `VIDEO_MEETING_NOT_STARTED` until the side's player has a COUNTED CHECK-IN (owner, 2026-11-17): the meeting row for the current pairing is still required, but it no longer suffices, because with `EXTERNAL_PLAY_PREMINT=1` pre-mint writes the meeting row before anyone arrives, so "a room exists" no longer means "the player came". A club in shadow mode still watches every player who has checked in.
- **Presence is read through plan 1's readers, never a hand-rolled query** (`server/external-play/video/presence.ts`, plan 1 final): the flag-ON refusal calls `everJoined(db, { meetingId, participantId, customParticipantId })` ("has this participant EVER had a presence row, any source, open or closed"; plan 1 exports it for exactly this refusal so the match rule ships once). - **Either flag state, a side with no player participant on file is not joinable** (review row 12): a QR self check-in counts for an online board with no seat and no participant, and an admitted join with `players: []` would connect, unsubscribe every peer (the guard in `arbiter-camera.ts` keeps only `players`) and show nothing with no error. The join refuses `VIDEO_MEETING_NOT_STARTED` before any vendor call when the side's `preset = 'player'` rows for the side's person are empty.
- **One predicate for "the player has arrived"**: `arbiterSideAdmits({ proofFlag, presenceEver, checkInCounted, playerParticipants })` (pure, exported from `arbiter.ts`) is `playerParticipants > 0 && (proofFlag ? presenceEver : checkInCounted)`. The join (Task 1) and the loader's `joinable` mark (Task 3) both call it, each over facts it read itself. The facts are monotonic within one pairing (a counted check-in stays counted inside the window, a presence row is never deleted, a participant row is never deleted), so a side the loader calls joinable is not refused NOT_STARTED by a later join except across a flag flip; Task 3's re-open on the next poll covers that case.
