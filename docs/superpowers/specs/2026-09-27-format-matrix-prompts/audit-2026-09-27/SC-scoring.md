## How results reach standings (read, shared by every sport)
- **There is one write path.** The pad at any fidelity band ("Result only" = band 0), "Enter final score", device links, API batch import (`event-import.ts`) and v1 all append events through `appendEventInTx` (`apps/web/src/server/engine-db/append-event.ts:252-420`). Each append strict-folds the whole stream and writes `fixtures.outcome` and `match_states.state`.
- **Standings read what the pad wrote.** They use `standingsDelta(outcome, resolveFixtureCfg(...), ctx, match_states.state)` (`competition.ts:305-352`). Manual entry therefore cannot drift from the pad at the storage seam. A parity gap can only be about WHICH band-0 events a sport offers (football/hockey/carrom have no one-shot final-score event).
- **One config resolver.** `resolveFixtureCfg` is shared by the write fold, the read fold and standings (`fixture-cfg.ts:39-46`, `append-event.ts:270`, `fold.ts:155`, `competition.ts:325`). It is frozen onto `config_snapshot` at the first event (`append-event.ts:280,365`).
- **Per-stage rules overlay.** `stageScopedCfg` (`stage-cfg.ts:18-40`) applies `rules` (tennis/badminton/TT/volleyball only; `stage-rules.ts:152-158`, `match-rules.ts:956-961`) plus the stage deciders `shootout` and `extraTime`. No organiser UI writes the deciders; only API v1 `CreateStage` does.
- **Knockout guard.** `append-event.ts:334-346` refuses ONLY `outcome.kind === "draw"` when `supportsDraws` is false. The advance paths are `advancingSides` (`fed-seats.ts:97-103`) and `bracketWinnerLoser` (`competition.ts:151-165`). Both yield no winner for draw, tie and no_result, so a `tie` or `no_result` commits and seats nobody.
- **Ratios are safe from division by zero.** They cross-multiply integer ledgers, never divide (`competition/tiebreakers.ts:293-349`). Display comes from `competition/display.ts:23-80`: ∞ when unbeaten, — with no ledger. `game_ratio` has no derived column.
- **Abandoned knockout matches.** By owner ruling 2026-09-21, an abandoned KO match with an outcome is NOT a dead feeder and stays stuck and visible (`stages.ts:3628-3658`). There is no first-class "decide by lot / higher seed" event; see X3.

## Key facts established (read)

- **Only one result-entry path for these sports**: the pad. Band-0 "result only" = `badminton.game.summary` / `tabletennis.game.summary` / `volleyball.set.summary` / `tennis.set_summary`, all folded through the same strict `apply` as rallies (`append-event.ts:270` → `resolveFixtureCfg`). No bulk import or API path produces a coarse result for these sports (`imports.ts` has no score/summary producer; `git grep set.summary|game.summary|set_summary` hits only pad skins + dictionaries). So manual-vs-pad parity is structural: one fold, one ledger.
- **Coarse events carry per-set points, required**: setbased `SetSummaryPositional {home, away}` both required ints (`setbased/kernel.ts:198-202`); nested `NestedSetSummary {home, away, tb?}` (`nested/kernel.ts:240-249`); `tb` REQUIRED in strict mode for a 7–6-form set (`nested/kernel.ts:1318-1323`). points_won/points_lost therefore persist from band 0. Exception: tennis summary sets contribute `points_won` only for tb/MTB points (not game points) — tennis does not rank on it.
- **Standings metrics**: setbased `sideMetrics` = sets_won/sets_lost/points_won/points_lost (`setbased/kernel.ts:2255-2260`); nested = sets_won/sets_lost/games_won/games_lost/points_won (no points_lost) (`nested/kernel.ts:2038-2049`). Ratios cross-multiplied, never divided (`competition/tiebreakers.ts:293-306, 324-327`); `x/0` = ∞, `0/0` = 0; display `ratioText` (`competition/display.ts:57-60`). `game_ratio` has no derived column but tennis shows games_won/lost as plain columns (`nested/kernel.ts:1453-1459`).
- **Setbased summary validation** is exact (`reachableSetScore`, `setbased/kernel.ts:474-489`): probe rejected badminton 21–25, volleyball 5th-set 25–20; accepted 29–30 (cap), 22–20, 15–13, 16–14. Tests pin 33–30 / 25–24 / 31–30 / 16–15(short) / 11–10 (`setbased.test.ts:106-226`, `boundary.test.ts:87-193`).
- **Draws** refused for both kernels in every stage (`setbased/kernel.ts:2471-2473`, `nested/kernel.ts:2223-2225`); abandon → outcome null + `replayFlagged` (`setbased/kernel.ts:818-823`, `nested/kernel.ts:1387-1392`); test `setbased.test.ts:270-289`.
- **Per-stage rules**: sets sports only (`match-rules.ts:956-961`); write path validates keys per sport + parses merged cfg + guards pointsMap on bestOf change (`stage-rules.ts` putStageRules); stage locked once any fixture has a snapshot or events. Pad (write fold) and read fold and standings ALL resolve cfg through `resolveFixtureCfg(snapshot, division.config, stage.config)` (`append-event.ts:270`, `fold.ts:155`, `competition.ts:323-331`), and the first event freezes the resolved cfg (`append-event.ts:280,365`). Parity ✅.
- **Bo1 set-sports trap** (#877) handled in the editor for badminton/TT/volleyball (`match-rules.ts:797-857`); tennis explicitly excluded.

## NRR subsection

- **Formula / site.** Ledger per fixture: `standingsDelta` (cricket.ts:3849-3884). `effectiveBalls` = the innings' `ballsLimit` when all out, otherwise `legalBalls` (3853-3858). Rank: `nrrFraction` = (rf·bb − ra·bf)/(bf·bb), exact integer cross-multiplication over **season aggregates** (competition/tiebreakers.ts:311-317, 338-342). Display: `6·rf/bf − 6·ra/bb`, toFixed(3), signed (competition/display.ts:68-75). Shown on the public standings table, standings-view and slideshow (apps/web standings-table.tsx, standings-view.ts, slideshow-data.ts). Default cascade: points → wins → nrr → h2h_points → seed (cricket.ts:3961).
- **Overs as balls (19.4 = 118 balls):** ✅ integer balls throughout. There is no decimal-overs input anywhere (the pad asks for balls).
- **Aggregate, not an average of per-match rates:** ✅ ledger sums then cross-multiplies (tiebreakers.ts:311-317).
- **All-out charged the full quota:** ✅ (cricket.ts:3854-3856; test cricket.test.ts:552-559).
- **Super-over runs excluded:** ✅ `ledger()` walks `state.innings` only (3864-3872; test 492-504).
- **No-result / abandoned excluded:** ✅ zeroed ledger, `no_results: 1` (3937-3943).
- **Forfeit excluded:** ✅ (3915-3921).
- **DLS / reduced overs:** ❌ In a match whose chase was cut and given a revised target (`applyRevise`, cricket.ts:1070-1135), ICC credits Team 1 with (revised target − 1) runs off Team 2's revised overs. The code credits Team 1's ACTUAL runs off its OWN balls (3864-3872). For a match decided on DLS par at abandonment (cricket.ts:1150-1177), ICC credits Team 1 with Team 2's par off the overs Team 2 faced. The code again uses Team 1's actual runs and full balls. DOMAIN.md:160 does not mention DLS, so the deviation is undocumented, and no test covers it.
- **Hundred (5-ball overs):** ⚠️ the display hardcodes 6 (display.ts:72), so a 5-ball-over division prints NRR per 6 balls. The ranking is unaffected because it compares per ball.
- **Team with zero balls (only NR / forfeits):** compareRatio treats d=0 as 0 (tiebreakers.ts:300-303), so the team ranks above every negative-NRR team while the display shows "—". Low.
