**R-B — multi-camera is wanted, later, with the seams shaped now.** Not parked,

switching, per-source `jitterBufferTarget`, cross-source NTP) — pre-building
those is the speculative generality `AGENTS.md` forbids.

Consequences: M3 becomes mandatory. M1 returns as ONE ROW in R0's bench rather
than a wave — if N-way WHEP decode does not fit an economic guest, "easy to
extend" is false at the compute layer however clean the interfaces are, and R0 is
already sizing that guest for 1x. M2 stays deferred as mechanism.

## The modelling decision that makes R-B cheap

**Multi-camera is N inputs under ONE session, not N sessions.** That keeps
`fixture_stream_sessions_one_active` correct as written (design §6.1), keeps
credits and the state machine per-broadcast, and keeps §7.4's "one Machine, no
fan-in" true.

So: extract `fixture_stream_inputs` (`session_id`, `slot smallint`, the ingest
columns that sit on the session row today, `created_at`). R1 and R2 write exactly
one row at slot 0. Multi-cam later inserts rows instead of migrating a shipped
table. An `inputs jsonb` column is rejected — no constraints, and this repo has
already been bitten by jsonb coercion reading a written value back as something
else.

## Six extras found while pinning the register

- **E1** Migration collision, and the standing rule that came out of it.
  Design §6.1 wanted `V402__stream_sessions.sql`; `main` has
  `V402__streaming_entitlements.sql`. §5.1 and §3.7 had the same problem — and
  §3.7 is the clearest evidence: it predicted `V400`, another wave took `V400`,
  and it shipped as `V401`. Three predictions in one document, three
  collisions.

  **Owner ruling 2026-09-10: a migration version is NEVER pinned in a design or
  a prompt.** The number is resolved when the task starts, by
  `ls db/migration/deltas | sort -V | tail -1`. Documents name the file STEM.
  Migrations that have LANDED keep their concrete numbers, because those are
  history rather than predictions. And if a migration is written but not yet
  merged, AMEND it rather than adding a forward-fix — a duplicate Flyway
  version survives a clean rebase and reds late, far from its cause.

  A consequence found while applying it: R1 was about to brief
  `V40x__streaming_relay_entitlement.sql`, writing `streaming.relay` rows for
  the five v18 plans. `V402` already shipped BOTH keys for all five, `false`
  everywhere. The migration was a no-op that would have burned a version
  number. R1 now owes no entitlement migration at all.
- **E2** `_STATE.md` says "read this first" and is two days stale — still names W1
  as next and #752 as unmerged.
- **E3** The G1 blocker is two conditions, not one. See Blockers.
- **E4** Design §6.1 says RLS is enabled on "all three tables" and defines two.
- **E5** Design §6.3 returns `503 storage_exhausted`; §6.4 lists
  `storage_exhausted` as a `failed(reason)` state. They disagree on whether that
  condition ever creates a row.
- **E6** §9a makes ports-and-adapters binding, and `RunnerProvider` is a port
  named but never defined — §7.1 says only "the `RunnerProvider` port stays, so a
  second driver is one file later". The pattern is cited, not honoured.

## Method

Four of the register's claims are re-pinned against this tree and hold: `muted` is
real and §7.3 specifies nothing; §7.2 names neither `module-null-sink` nor
`set-default-source`; §7.6 carries SRT only; and no compositor code exists.

**The other eighteen are unverified.** Each is re-pinned as it is folded. A row
that fails is recorded as a finding against the register, never silently dropped —
the brief is a hypothesis, a grep is not a read, and a read is not a run.
