## False premises found (record these, do not re-derive)

### F1 — `finalRanks` is readable ONCE, in a POST response, and never again

B05 §3 requires an end-state oracle on `finalRanks`, and B02 added
`expected.finalRanks` to the frozen `PackSchema` expressly for this wave
(`bench-prompts/_INDEX.md`, 2026-09-02 entry). But `finalRanks` exists ONLY as
an internal engine identifier — `apps/web/src/server/engine-db/competition.ts:487-499`,
inside the `stage_completed` event payload. It is serialised on no `/api/v1`
response; a grep for `finalRanks\|final_ranks` across `apps/web/src/server`
returns five hits, all in that one file.

Follow-up pin settles where it IS reachable, and the answer constrains the
runner's control flow rather than merely its assertions:

- `POST /api/v1/stages/{id}/complete` returns `CompleteStageResult` =
  `{ completed, events, qualified?, next_stage_fixtures?, division_completed?,
  seed_proposal? }`, and for a ladder/bracket completion `events` is
  `[{ type: "stage_completed", stageId, finalRanks }]` — returned as-is
  (`engine-db/competition.ts:428-430,498,553`). **This response is the only
  time final ranks cross the wire.** Emitted for EVERY stage kind, not only
  ladder/bracket as first recorded here (corrected by T3):
  `packages/engine/src/competition/stage.ts:237` table/pool via
  `crossPoolOrder`, `:275` bracket via `bracketRanks`,
  `engine-db/competition.ts:498` ladder via `config.ladder_order`.
- `GET /api/v1/divisions/{id}/history` (`usecases/history.ts:375-397`) selects
  only `seq, type, actor_id, created_at` from `division_events`. The `payload`
  holding `finalRanks` is NOT selected, so the ranks cannot be re-read later.
- `GET /api/v1/fixtures/{id}/events` (`route.ts:21-29`, `?since_seq=`) is the
  per-fixture SCORE ledger — a different stream from `division_events`.

Consequence for B05: the simulate/advance step must CAPTURE the complete-call
response at the moment it advances; a later re-read cannot recover it. The
re-readable counterpart is `rank` on the standings rows
(`competition/progression.ts:716-730` sets `rank: i + 1` from `finalRanks`),
which is also the customer-visible one.

### F1b — there is no champion field anywhere

Grep for `champion|winner_entrant|division_winner` across
`apps/web/src/server` and `apps/web/src/app/api/v1`: zero code hits (only
marketing copy in the dictionaries). Bench spec §8's "engine-derived champion
== history" therefore has no field to read. The two candidates are `rank: 1`
in the final stage's standings, or `finalRanks[0]` in the complete response.
Product finding for spec §15 — the product has no champion concept on the
wire.

### F2 — the stage-advancement symbols live in `stages.ts`, not `stage-seeding.ts`

`computeSeedProposal` (`usecases/stages.ts:2877`), `confirmSeedProposal`
(`:3041`), `completeStage` (`:2331`), `generateStageFixtures` (`:1095`).
`usecases/stage-seeding.ts:73-296` holds only `resolveProgressionSource`,
`sourceStandingsTables` and helpers — none of the four.

### F3 — `import.events` HAS a `plan_entitlements` row

B00's inventory recorded the batch import endpoint as feature-gated with "no
`plan_entitlements` row yet", true at its origin migration (V376, whose comment
says deliberately out of scope). `V396__public_public_by_default_and_share_loops_paid.sql:38-44`
inserts `import.events` as bool TRUE on all five plans
(community/pro/enterprise/event_pass/event_pass_l). The V376 comment is
superseded and reading it alone gives a stale answer.
