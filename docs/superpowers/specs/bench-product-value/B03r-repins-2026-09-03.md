## Two more findings, from pinning the API surface

### FP6 — the funnel oracle's `paid_cents` source is wrong

Design §5.2 gates on: *"Σ paid `registration_groups.amount_cents` ==
`expect.paid_cents`"*.

But `registration_groups.amount_cents` is a **submit-time snapshot that the
payment path never touches**. On `checkout.session.completed`,
`confirmPaidRegistration` (`usecases/registrations.ts:2762`) updates:

| Table | Columns written |
|---|---|
| `registrations` | `status = 'paid'`, `charged_at = coalesce(charged_at, now())`, `payment_intent_id` (`:2894-2899`) |
| `registration_groups` | `payment_intent_id` only (`:2902-2905`) |

The status page's own comment (`status/page.tsx:90-92`) says the same thing:
`amount_cents` is a submit-time snapshot.

So summing `amount_cents` across groups counts money that was **never paid** —
an unpaid entry contributes its full fee and the oracle reads green. That is
the "absent symptom means suppressed, not safe" class: the gate would pass
hardest exactly when payment is broken.

**Correction:** sum `amount_cents` only over entries whose `registrations.status`
is `paid` or `confirmed`, and additionally assert `payment_intent_id IS NOT NULL`
on each. Pin the value, not the reachability. Design §5.2 needs this correction.

Note the two terminal states: auto-approval divisions go on to
`status = 'confirmed'` with an `entrant_id` (`registrations.ts:1029-1030`);
manual-approval divisions **stay at `paid`** awaiting `approveRegistration`.
An oracle that only accepts `confirmed` reds every manual division; one that
only accepts `paid` reds every auto one. Both are required.

### FP7 — "blocked on eligibility" is two different error codes

Design §5.2 requires each `rejected_eligibility` offender to be blocked at
public submit **and** blocked if the organiser tries to force it in. Those are
two different code paths throwing two different strings:

| Path | Symbol | Code |
|---|---|---|
| Public submit | `registration-submit.ts:1201-1211` → `eligibilityError` `:325-327` | `HttpError(422, …, "ELIGIBILITY")` |
| Organiser force | `registration-eligibility.ts:342-364` `gateRosterEligibility` (called only from `entrants.ts:203`, `fixtures.ts:360`) | `"ELIGIBILITY_VIOLATION"` |

A driver matching on one code proves only one half of the gate. Assert
`issue.code` per endpoint, never a shared substring.

### The predicate itself lives somewhere else again

Not in `registration-eligibility.ts`. The age/category arithmetic is
`ageBandEligibilityIssues`, **`apps/web/src/lib/registration-rules.ts:302-311`**:

```
const cutoffDate = new Date(Date.UTC(seasonStartYear, cutoffMonth - 1, cutoffDay));
const age = ageAt(person.dob, cutoffDate);
if (division.age_max != null && age > division.age_max) { … AGE_TOO_OLD … }
if (division.age_min != null && age < division.age_min) { … AGE_TOO_YOUNG … }
```

`cutoffMonth`/`cutoffDay` default to 1/1 when null (`:271-272`); `ageAt`
(`:56-64`) is whole years vs `dob`, decremented if the date falls before the
birthday. Stage-0's rule 1 derives from THIS, not from arithmetic typed into
the bench.

## A sixth stage-0 rule, found by checking a testid rather than trusting it

Design §4 lists five stage-0 checks. There is a sixth, and it was found only by
opening the control the `reg-consent-grant` testid had been attached to.

`StepConsent` (`components/public-site/register/step-consent.tsx`) is shared by
the public stepper AND the join form (`join-form.tsx:233`). It renders three
consent controls:

| Control | id | Role |
|---|---|---|
| privacy consent | `reg-consent-privacy` | REQUIRED — gates submit. Now also `data-testid="reg-consent-grant"` |
| media consent | `reg-consent-media` | optional, never blocks |
| guardian consent | `reg-guardian-consent` (`:144`) | only rendered when `showGuardian` |

And `:54`:

```
const showGuardian = guardianRequired(cart, contact, new Date());
```

So the guardian block **only exists when the person's `dob` makes them a minor
at run time**. A pack declaring `joins[].consent: "guardian"` for a person whose
`dob` makes them an adult would find no guardian control at all — the browser
driver would hang on a selector that never appears, and the http driver would
send a body the route rejects or, worse, silently accept a plain grant.

**Sixth stage-0 rule:** `consent: "guardian"` requires the joining person's
`dob` to make them a minor against the same predicate the product uses
(`guardianRequired`, `components/public-site/register/validation.ts`), not
against arithmetic invented in the bench. Fails offline in seconds instead of
mid-run.

This is the class the programme keeps paying for: a reachability test is
satisfied by ANY value. The testid was correctly placed and the tests were
green; the defect was in what the pack could legally *say*.

Note the guardian control is left untagged deliberately — `reg-guardian-consent`
is already a stable non-text `id`, and the owner's ruling was not to add a
parallel selector layer where one exists.

## Corrections to THIS file, found by building against it

The pin table above is itself a hypothesis. Two entries were wrong, both
caught by an implementer reading the route files rather than trusting the

### C1 — `join_code` is a BODY field on the POST, not a query parameter

The table said
`POST /api/v1/public/orgs/{org}/competitions/{comp}/register/join?join_code=…`.

Wrong. The POST takes `join_code` in its body (`PublicJoinRequest.join_code`);
confirmed from `join-form.tsx`'s `joinSubmitUrl` / `buildJoinBody` and from the
route's own GET/POST split. The `?join_code=` form belongs to the **GET check**
path (`publicJoinCodeCheckPath`, `…/register/join/view-model.ts:60,64`) — a
different request for a different purpose.

The original scout report listed both, and the pin table collapsed them into
one row. A driver built from that row would have posted a body the route reads
as empty. Now regression-tested directly.

### C2 — `ELIGIBILITY_VIOLATION` is NOT reachable from any organiser action

FP7 above says design §5.2 needs an offender blocked at public submit **and**
blocked when the organiser tries to force it in, and names the two error codes.
The first half is real. The second half **cannot be exercised by B03r's driver
at all**: `gateRosterEligibility` is called only from `usecases/entrants.ts:203`
and `usecases/fixtures.ts:360`. Neither is reachable through
approve / reject / promote / assign — the four organiser actions the driver
performs. Those paths are entrant creation and fixture generation, which is
**B04 territory**.

So design §5.2's organiser-force half is not provable in B03r. It is provable
in B04, where entrant creation runs. This is a **sequencing correction to the
design, not a defect**: the funnel oracle as specced cannot be fully satisfied
by the session that owns it.

The mapper handles both codes defensively anyway, so nothing has to change when
B04 makes the second path reachable — but the gate must not CLAIM to have
proven the organiser-force half until then. An oracle asserting a branch
nothing can reach is the vacuous-gate class: it passes because it never runs.

### C3 — `npx vitest` is intermittently unusable in this worktree

`npx vitest` here sometimes exits 254 with
`ERR_PNPM_RECURSIVE_EXEC_FIRST_FAIL` (no root vitest bin), and sometimes runs
fine — observed both within minutes, same cwd, same command. When it fails it
writes **no JSON file at all**, so a run that judged only `numFailedTests`
against a stale or absent report would read as green.

Two consequences: always confirm the JSON file was actually written this run,
and prefer `./packages/engine/node_modules/.bin/vitest` when `npx` flakes.
