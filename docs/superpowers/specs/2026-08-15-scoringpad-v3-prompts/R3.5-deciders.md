## Why this wave exists

R2 shipped cricket and R3 shipped football, both signed off. Neither sport's
**tie-breaker** was ever rendered to the owner, because the gallery harness has
no tie-break state: it runs `01-pre` … `10-reviewblocked` and stops. Every
defect below was invisible to unit tests, to `tsc`, and to a 15/15 visual
sign-off, for that one reason.

**The engine is not at fault in any of this.** Cricket resolves a tie into a
super over, continues the innings count, and carries all three still-tied
policies. Football pushes `SHOOTOUT` at full time, enforces alternation and
early-decides through the shared `period/shootout.ts` primitive. Everything
here is the pad, plus one unreachable cfg pair.

## The defect, in one line

`currentInnings` (`skins/cricket.tsx`) reads `state.innings`. The engine keeps a
super over in `state.superOver.innings`. Everything cricket-side follows from
that.

Verified on merged main `5f2951945`, folding a real tied T20:

```
phase                 super_over
engine superOver runs [6]
pad currentInnings    150          <- the closed second innings
pad scorebug          ["150/7", "20.0"]
tiles enabled         ["toss", "more"]
```

In the ball-by-ball lane the numbers differ and the shape does not: **fifteen of
sixteen tiles carry `disabled`**, the context strip prints *"This innings is
closed."* three times in red over a live board, and the More sheet does not
offer the Super over panel that `padSpec` declares for exactly this phase.

## False premises found (verified in the tree, before any code)

- **"The client cannot import the engine"** (S10, carried forward in v2's index)
  is STALE for v3. `skins/cricket.tsx:90` imports three runtime helpers from
  `@seazn/engine/sports/cricket` today. R3.5-3 depends on this being false.
- **The `_INDEX.md` Order row said `R4 | TODO`** while R4 was 34 commits in
  flight with its own row reading `IN FLIGHT`. Two rows, one wave, disagreeing.
- **The review artifact's first read said football's pens were invisible.** They
  are not — `pad-host.tsx` renders the engine's `summary.headline`, so the band
  above the scorebug reads `1 — 1 (2–1 pens)`. The defect is narrower and worse
  in a different way: two score readouts on one screen, disagreeing.

## Tasks

Each ships a test that fails without it. Order matters: A first so every later
fix is provable as a before/after pair.

### A — capture the broken states (no production code)

Add four gallery states and publish the **before** artifact ahead of any fix:
`11-superover`, `12-superover-decided` (cricket), `11-shootout`,
`12-shootout-decided` (football). New surfaces, so they also join the
seven-width `mobile.spec.ts` matrix and get an axe scan — the tie-break states
have never been contrast-scanned in the product's history.

### B — a disabled tile must not claim its event type  (chassis)

`dedicatedEventTypes` harvests `tile.action.event.type` from every tile whether
or not it is disabled, so `moreActions` drops a panel as "already reachable
through a narrowed surface" when that surface is greyed out. Skip disabled
tiles. Shape on merged main is
`dedicatedEventTypes(tiles, sheets, swaps, scorebug)`; the guard is one line in
the tile loop.

R4's own comment on this function documents the **third** instance of
*reachable-but-still-listed-in-More* and explicitly warns against calling it the
last. This is the fourth, inverted. Extend that comment; do not start a new one.

Test: a skin with a disabled tile for type X leaves X in `moreActions`.
Mutation-proof it — flip the guard, the test must red.

### C — cricket: one definition of the innings being played  (blocker)

Per R3.5-3. Export the switch from the cricket module; `currentInnings`
delegates; `CricketStateShape` declares `superOver`. `chaseTarget` gains the
super-over rule the engine already applies in `applySuperOverBall` (second SO
innings target = first + 1).

Closes findings 1, 2 and 3 together: tiles re-enable, the scorebug tracks the
super over, run rate / target / bowler come right, the three red closure lines
stop.

Engine change is **additive export only** — no fold change, no serialised-state
change, so the frozen golden corpus is untouched and no re-baseline is owed.
Engine has its own lint task and a 100% core coverage threshold; run both.

**An existing e2e will go red, and that red is correct.**
`e2e/scorepad-v3-cricket.spec.ts:1004` sets `superOver: true` deliberately to
reach a tie, then asserts the tiles are disabled, the closure message is
visible, and the scorebug keeps the previous innings' score. It pins the defect
as intended behaviour. Rewrite it to assert the terminal case it meant to test
(a tie with `superOver: false`) and add a super-over case beside it.

Test the skin against a **real fold** (`foldMatch` + `cricket.superover.ball`),
never against a mirror of the engine — a mirror agrees with itself, which is how
R3 shipped four dead-end paths.

### D — a scorebug half can carry a second figure  (chassis)

`ScorebugHalf` gains optional pre-formatted `sub?: string`, rendered small
against `big`. Football fills it during `SHOOTOUT` so the board reads `1 (2)`
instead of contradicting its own headline (design note D-11: one score,
rendered once).

Chassis field, not a football string, because **R6 needs it next**:
`period/kernel.ts` already composes `2 — 1 (GWS 2–1)` for icehockey and hockey.
Contrast computed from tokens, then axe.

### E — the kick log names the side

`footballDetail` renders a shoot-out kick as outcome + optional person, no side.
Four rows of *Scored / Scored / Missed / Scored* from which 2–1 cannot be
reconstructed — and it is the panel a scorer voids from, so a mis-tap is
corrected blind. New keys → all four dictionaries + `i18n:gen-keys`.
`git grep -a` the old AND new strings across `e2e/` before editing.

### F — the board says whose kick is next

`expectedKicker()` is already exported from the shared primitive and the pad has
never called it. Surfacing it prevents the out-of-turn 422 rather than
explaining it — which matters because server refusals are not localised and
reach a Spanish or Dutch scorer in English.

### G — a decided fixture says who won, and how

The public fixture page already receives `fixture.outcome` (winner, and
`method: "shootout" | "super_over" | "boundary_count"`) and renders none of it.
One sentence, four locales. The same `summary` feeds the WhatsApp share text and
the OG description, so this single change lands on the fixture page, in the
message parents receive, and in the link preview.

### H — football stops forking the shoot-out tally  (engine)

`football.ts`'s `summary()` hand-rolls a third copy of a tally `shootout.ts`
exports and `period/kernel.ts` already uses. Inert today (football never sets
`void` on a kick), live the moment football adopts retakes — at which point the
displayed tally and the decision diverge while every test stays green.

### I — group-stage shoot-out points reachable  (per R3.5-4)

Two fields in the match-rules editor for `shootoutWin` / `shootoutLoss`. Needs a
standings test: a group fixture decided on kicks must award the split, not flat
win/loss.

### J — phase-gated kick tiles  (per R3.5-5)

A pair of kick tiles visible only in `SHOOTOUT`, in the space the Goal tiles
vacate. Depends on B (the More panel must remain correct for any band that still
reaches it).

### K — structured logging on the decider path

`appendEvent` (`apps/web/src/server/engine-db/append-event.ts`) is the single
funnel every scoring event passes through and it logs **nothing**. Every
super-over ball, every shoot-out kick and every engine refusal on both is
invisible in production — which is why this wave's defects had to be found by
rendering the pad rather than by reading a log.

Instrument it with the existing pino singleton (`@/server/logger`): `info` on an
accepted event and on the two decider transitions (entering `super_over` /
`SHOOTOUT`, and resolving one with `outcome.method`), `warn` on an
`EngineError` refusal, re-thrown unchanged. IDs, types and codes only — a
payload carries person ids and consented names, and a log line is not a
consented surface.

Not in the skins (`"use client"`; `@/server/**` in a client component is a build
failure `tsc` cannot see) and not in the sport modules (`packages/engine` is
zero-effectful-deps by declaration; `scheduling/logger.ts` is a scoped,
unexported exception, not a precedent).

### Task R — Task C moved the ground under three sibling derivations

Repointing `currentInnings` at the super over was the right fix and it was
not enough: three OTHER derivations read that same value and none was
re-examined.

- `inningsClosed` (`skins/cricket.tsx:1164`) went false during an open
  super-over innings, so `closedTile` stopped disabling `review`, `retire`
  and `inningsClose` — all three of which the fold refuses in `super_over`
  (`requireOpenInnings`, `cricket.ts:1746`; innings-close, `:3134`). Three
  dead-end taps that were correctly disabled BEFORE the fix.
- The coarse over tile is offered with no super-over innings yet, where
  `cricket.innings.summary` is refused (`cricket.ts:1481`). Case C2
  (`skins/__tests__/cricket.test.ts:2891`) pinned that as intended.
- **A tied super over reproduces the original bug, one pair later.**
  `superOverStillTied` defaults to `"repeat"` (`cricket.ts:65`); with pair 1
  closed and pair 2 not yet created, `dueBattingSide` returns null and
  `blockedByClosure` disables the whole delivery row while the fold accepts
  the next ball. Case C12 (`:3012`) folds a ball of pair 2 before asserting,
  so it cannot see the window.
- Same window shows the finished pair's target.

**The ruling this earns.** `PadPhase` is a closed three-value set and
`super_over` maps down to `"live"` (`resolvePhase`, `:987`), so a
`phases: ["live"]` declaration CANNOT express "not during a super over".
Any such gate is on the engine phase, and the engine phase alone.

### Task Q — the standings-points editor wrote keys no sport reads

Task I is the first field to persist a nested `points.*` key the engine
actually reads. Doing so exposed that the block around it never worked:

- `w`/`d`/`l` appears in exactly one schema, `generic.ts:37-39`. Football
  (`football.ts:110-112`), cricket (`cricket.ts:56-58`), the period kernel
  (`period/kernel.ts:196`) and the nested kernel all use `win`/`draw`/`loss`.
  Zod strips unknown keys, so `division-settings.tsx:418-423` has been
  writing discarded keys and reading `undefined` for every real sport.
- `Object.assign(override, buildRuleOverride(...))` (`:417`) replaces
  `points` WHOLESALE, and the standings-points block immediately after
  overwrites whatever survived.
- `ruleValues` (`:270`) is never hydrated from `division.config`, though
  `pointsW/D/L` beside it are — so re-opening Settings and retyping one
  field drops its sibling, and the engine's split needs both defined
  (`football.ts:2599-2603`).

**Behaviour change, flagged not hidden:** a division that saved non-standard
`w/d/l` had them ignored; once the editor writes `win/draw/loss` those
numbers start counting. That is what the organiser asked for.

**Why it shipped green.** The e2e set config through `mergeDivisionConfig`
(the API) and the unit tests asserted `buildRuleOverride`'s RETURN VALUE.
Nothing exercised form → persisted config. A returned object is not a saved
one.

## Task L found what nothing else could — and it was a blocker

Task L drives both deciders BY HAND: setup may use the API to REACH a
decider, but every event that IS the decider is TAPPED, and the ledger must
agree with the tap. `apps/web/e2e/scorepad-v3-deciders-byhand.spec.ts`.

On the first tapped super-over delivery, against the built prod server:

```
422 INVALID_EVENT — "bowler V3 TLCR Away1 … is not in the fielding lineup"
```

Home batted first, so away bats the super over and HOME bowls. The pad
proposed all three roles from the wrong sides — the bowler from the side
that was batting. **A super over could still not be scored by hand**, after
Tasks C and R both closed on it.

**Root cause — the FOURTH sibling.** `resolvePeople`
(`skins/cricket.tsx:495-524`) reads `scoringInnings` (`:426`), which is
`dueBattingSide(...) !== null ? null : currentInnings(state)`. At the start
of a super over `dueBattingSide` returns null (the `so.length === 0` arm)
and `currentInnings` yields null (in the super over, empty list), so
`battingSide` falls through to a literal `?? "home"`. Task C repointed one
derivation; Task R fixed three siblings; this is the fourth, and the only
one that actually blocked scoring.

**Why no test caught it.** Cricket's existing e2e drives its super over
entirely through `postEvent`. Not one super-over delivery in the suite had
ever been TAPPED, which is exactly how the original R2 defect survived its
own sign-off. A test that posts the payload it expects cannot discover that
the pad builds a different one.

Task K's logging paid for itself the first time it was needed: the refusal
arrived with fixtureId, eventType and code already structured, so the
diagnosis started from the fact rather than a guess.

**What Task L also confirmed, in a real browser** — Task R's gates hold:
Review, Retire, Close innings and End of over all render `[disabled]` in a
live super over while every delivery tile is enabled, and the "This innings
is closed." message is gone.

**One correction to the harness, not the product.** Task L's first football
assertion read `payload.outcome`; `FootballShootoutKick` is a `strictObject`
of `{ by, scored: boolean }` (`football.ts:283-293`) with no such field.
Fixed to assert `scored`. The test was wrong; the pad was right.

## Owner rulings on the two open questions (2026-08-27)

Both went the way the recommendation argued. Recorded here because neither
is derivable from the code, and a fresh session will otherwise re-open them.

**R3.5-7 — the decided sentence's new placement STANDS.** Task O moved it
from a static paragraph above the subheading into `LiveScore`'s own render,
just above the scorebug. It had to move into the client component to update
without a reload, which is the behaviour the owner ruled a must-have. Do NOT
"restore" it to the server-rendered position: that silently reverts the live
update, and the e2e that guards it
(`scorepad-v3-football.spec.ts`, "decided sentence updates live") asserts the
sentence appears on an already-open page with no navigation, so moving it
back server-side reds that test rather than passing quietly.

**R3.5-8 — the disabled-primary-tile styling is R7's, not this wave's.**
At 320 a disabled `kind: "primary"` tile (e.g. "End of over 1" in a super
over) keeps a solid purple fill at `disabled:opacity-40`
(`tile-grid.tsx:252`), while a disabled secondary goes to outlined grey — so
the primary reads as tappable when it is not. It is legibility ONLY: the
button carries the native `disabled` attribute, so a browser never fires its
onClick and no dead-end tap is possible. The class lives in the shared
chassis and applies to every skin's primary tiles, so changing it here would
be blast radius inside a remedial wave. R7 (universal console) owns tile
chrome and takes it.
