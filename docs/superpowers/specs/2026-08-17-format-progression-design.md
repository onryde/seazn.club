# Competition format progression — design of record

**Status:** draft for owner review, 2026-08-17.
**Goal in one line:** an organiser picks any format, customises it, and sees
every fixture — including the final — on day one.

Programme dir (to be created on approval):
`docs/superpowers/specs/2026-08-17-format-progression-prompts/`.
Register in `bench-product-value/_MASTER.md` once approved.

## 1. The ask

Owner, 2026-08-17: *"as an org, I can choose any format with customization and
I want to see all fixtures including final from day one."*

Plus a defect spotted in the same session: bracket rounds reading
"Final, Final, Final" instead of Quarter-final → Semi-final → Final. Where that
is and is not true turned out to be the more useful finding — see §2.3.

## 2. What is true today — measured, not assumed

Every fixture list quoted here was generated by running the real generator
(`previewDivisionFixtures`) over every format the platform ships. 25 cases:
12 picker templates, 5 hand-built custom graphs, 8 catalogue templates.

**Two vocabularies describe progression, and a stage may hold only one.**
`stages.ts:217-222` returns 422 `SEEDING_RULES_MISSING` when a stage carries
both `qualification` and `seeding`, so the two populations never overlap.

| field | written by | fixtures appear |
|---|---|---|
| `qualification` | `createStages` — the picker and the custom builder | only when the source stage completes (`seedNextStage`, `stages.ts:1763`) |
| `seeding` | `createStages` and `instantiateTemplate` (`templates.ts:327`) — in practice only the catalogue templates | **at setup**, with placeholder slots (`generateSeededStageFixtures`, `stages.ts:1376-1505`) |

**Every multi-stage picker template uses `qualification`. None use `seeding`.**
Verified across all 12: `league_ko`, `groups_ko`, `group_stepladder`,
`group_playoffs` are all `-Q`; the rest are single-stage. So the day-one gap is
total on the path organisers actually use, not partial.

The machinery for the ask already exists and works — it is simply unreachable
from the picker. `fixtures.home_entrant_id` has been nullable since
`V214__fixtures.sql:12-13` ("null = TBD/bye"); `V360__stage_progression_seeding.sql`
added `stages.seeding`, `fixtures.home_slot_label/away_slot_label` and
`stage_seed_proposals`; the scheduler explicitly handles an entrant-less fixture
rather than skipping it (`participants.ts:119-143`); and the owner ruling is
already quoted in code at `stages.ts:866-877` — *"ALL stages' fixtures are
generated at setup time with placeholder slots"*.

### 2.1 Neither vocabulary is a superset of the other

This is the crux, and it is why "just delete one" is not available.

**Only `seeding` can express** (`stage-seeding.ts:42-52`):
- `topNPerGroup` / `bestNth` — patterns that expand across however many groups
  exist, rather than enumerating pool/rank pairs by hand.
- `placement: "snake"` — wave-major pot reversal.
- `placement: "seeded_map"` — explicit slot overrides validated against
  descriptor keys.
- the TBD generation path itself.

**Only `qualification` can express** (`qualification.ts:16-47`):
- `CombinedQualification` — several specs unioned with dedupe, **each with its
  own `from?` naming a different source stage**. `seeding.source` is singular.
  A crossover such as "group winners, plus the two best runners-up from a
  different phase" is expressible in `qualification` and not in `seeding`.
- `RoundLosers` — losers of a bracket round, landing now in L3/#414 (KO→plate).

### 2.2 Three formats cannot have day-one fixtures, ever

Swiss, americano, mexicano and ladder pair from live results. The generator says
so itself: *"Round 1 is seeded; the remaining rounds pair players on equal
scores from the live standings"*, and for ladder *"No fixed fixtures — players
challenge others within range and climb over a long window."*

This is arithmetic, not a missing feature. A final sitting **above** such a
stage can be pre-created; the rounds beneath it cannot. The product must say so
plainly rather than appear broken.

### 2.3 Round naming: one bad namer, and three good ones that disagree

Two separate problems, and the visible one is not the important one.

**The count-based namer is preview-only.** `roundTitle` (`stages.ts:746-753`)
names a round by match count — `1 → "Final"`, `2 → "Semi-finals"`,
`≤4 → "Quarter-finals"` — which titles every stepladder round "Final", calls a
page playoff's Qualifier-1-plus-Eliminator round "Semi-finals", and renames
rounds when a bye changes the count. Its **only** caller is
`previewDivisionFixtures` (`stages.ts:833`), so this reaches the marketing
gallery and help preview, not an organiser's schedule.

The clearest instance is a double elimination of 8, where the count heuristic
produces **four sections titled "Final" and three titled "Semi-finals" in one
bracket**, because a losers' bracket has repeated 2-match and 1-match rounds by
construction:

| rendered | actually |
|---|---|
| Quarter-finals | winners' R1 ✓ |
| Semi-finals | winners' R2 ✓ |
| Final | **winners' final** |
| Semi-finals | **losers' R1** |
| Semi-finals | **losers' R2** |
| Final | **losers' R3** |
| Final | **losers' final** |
| Final | **grand final** |

The wiring underneath is correct — the grand final reads
`Winner of R3·1 v Winner of R10·1`, i.e. winners' final against losers' final.
Only the labels are wrong, and every row already knows its lane
(`bracket: "WB"|"LB"|"GF"`) at generation time.

**The real path has three independent implementations.** All use distance from
the final rather than match count, so none carries the bye bug — but they have
drifted from each other:

| surface | mechanism | i18n |
|---|---|---|
| `public-site/bracket.tsx:385-397` + `PP_LABEL:432` | distance-from-end; names Qualifier 1 and Eliminator **distinctly** | **hardcoded English, no `msg()` at all** |
| `v2/stages-panel.tsx:1091-1105` | same algorithm, reimplemented; **collapses Qualifier 1 + Eliminator into one "Qualifiers"** | `msg("schedule.bracket.*")` |
| `v2/bracket-panel.tsx` | visual tree, no textual knockout round names | `msg("bracket.*")` |

Two consequences beyond the drift: the **player-facing** bracket violates the
4-locale policy outright, and the two i18n namespaces (`bracket.*` at
`i18n-keys.ts:978-989`, which has no semi/quarter key, and `schedule.bracket.*`
in `dictionaries/en/ui.json:1583-1584`) describe the same concept twice.

**The root cause is that the answer is computed and then discarded.** Generated
bracket fixtures carry `bracket: "WB"|"LB"|"GF"`, `isFinal` and `thirdPlace`
(`scheduling/bracket.ts:19-22`), but `bracketToGen` (`stages.ts:511-530`) copies
only `extKey`/`roundNo`/`seqInRound`/`home`/`away`/`homeFrom`/`awayFrom` when
persisting. The role never reaches the `fixtures` row — `V214__fixtures.sql:10-11`
stores numeric `round_no`/`seq_in_round` only — so every consumer must re-derive
from position. Three consumers, three derivations, guaranteed drift.

No test anywhere pins a round-name string on the real path, so nothing would
have caught the disagreement.

### 2.4 Bracket shape derivation already works

Given 6 qualifiers the generator produced an 8-slot bracket with two byes on the
top seeds, wired through to the final, with nothing specified:

```
[Quarter-finals] Seed 1 v TBD | Seed 5 v Seed 4 | Seed 3 v Seed 6 | Seed 2 v TBD
[Semi-finals]    Winner of R1·1 v Winner of R1·2 | Winner of R1·3 v Winner of R1·4
[Final]          Winner of R2·1 v Winner of R2·2
```

The pairing order is the standard bracket draw — (1,8) (4,5) (3,6) (2,7) with
seeds 7 and 8 absent, so the byes fall to the top two seeds. The geometry is
sound and this design does not change it. Two things around it are wrong:

- **A bye is rendered `TBD`.** A bye is known at setup and will never resolve to
  anyone. `TBD` tells an organiser to wait for something that is not coming; it
  should read `Bye`. F1 owns this.
- **Group separation is not expressible.** `topN: 6` flattens six qualifiers
  from two groups into one ranked list, so `Seed 3 v Seed 6` can be two teams
  from the same group meeting in the quarter-final — the thing a real draw
  avoids. Expressing "a group winner meets a runner-up from a *different* group"
  is exactly what `placement: "snake"` and `seeded_map` exist for, and the
  picker cannot reach them. **The picker cannot express a correct draw, not
  merely a late one** — the strongest argument for §3.

### 2.5 One customisation is silently unsupported

`League → top 3 → page_playoff` renders *"Preview isn't available for this
format."* A page playoff is a four-team shape. The correct shape for three
qualifiers is a **stepladder** (`Seed 2 v Seed 3`, winner meets `Seed 1`), which
works today. An organiser choosing "top 3 → final" has no way to know that.

## 3. Decision

**Unify onto one progression field** whose expressiveness is the union of the
two (owner chose this direction over the cheaper per-template fix). Reaching it
in one step is a rewrite; reaching it in two is a migration, because converting
the picker to `seeding` first moves every writer onto the richer vocabulary,
leaving one population to absorb rather than two to reconcile.

The unified field must carry, at minimum:

```
progression := {
  sources:  one or more { stage, take[] } groups      # from qualification.from/combine
  take:     rankRange | topNPerGroup | bestNth        # from seeding
          | picks[{pool,rank}] | roundLosers          # from qualification
  placement: rank_order | snake | seeded_map(map[])   # from seeding
  dedupe:   union semantics across sources            # from qualification.combine
}
```

`RoundLosers` needs a take-rule form so a plate bracket pre-generates like any
other. Without it, L3's KO→plate is the one structural format that still cannot
show its bracket on day one.

## 5. Migration — greenfield

**Owner ruling 2026-08-17: there is no production data.** Same stance as the
registration redesign: **no backfill, no dual-read, no compat shims, no feature
flags.** Drop `stages.qualification` and `stages.seeding` outright, add the
unified column, and make its constraints strict from day one — NOT NULL where
the shape demands it, CHECKs on every enum, no permissive interim state that
exists only to carry old rows across.

The discarded alternative, recorded so it is not re-litigated: an additive
column with a dual-read release and a backfill of both populations. That is the
correct shape when live rows exist, and it is strictly more work — a second
write path, a reconciliation, and a drop that has to wait a release.

Two consequences worth stating plainly:

- **The migration is destructive and not reversible by rollback.** Its
  correctness rests entirely on the zero-rows premise. F2's first step verifies
  that premise against the target database and **stops** if it finds rows,
  rather than trusting this paragraph — the premise is dated, and this document
  will outlive its accuracy.
- Because nothing has to be carried across, F2 does not need to split. The
  earlier estimate that it would (F2a/F2b, as RS001 needed RS001b) assumed a
  backfill. Five sessions stands.

## 6. Testing

Per standing policy, all four types per session, plus two specific to this work:

- **A generated-catalogue regression.** The 25-format dump that produced this
  document's evidence becomes a committed fixture: every format's stage graph,
  progression mode, and first/last fixture row. Any change that alters what a
  format produces has to update it deliberately. This is the artefact that would
  have caught the naming defect years earlier.
- **A day-one assertion per structural format**: after setup and before any
  result is entered, the final exists, with both sides unresolved and both slot
  labels populated.

Score-dependent formats assert the inverse — that their intermediate rounds do
**not** exist yet, so a future change cannot quietly claim to have solved an
unsolvable case.
